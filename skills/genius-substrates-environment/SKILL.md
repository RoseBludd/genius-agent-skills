# Genius Substrates Environment — Core Platform

The **Genius Substrates host** (`genius-substrates-host`, <tailnet-ip>) IS the core environment for everything Genius Substrates builds and runs. This skill is the index for that environment's services, env vars, and secrets — so future sessions know where things live and how to use them without re-recon.

> **Access first:** `tailscale ssh root@<tailnet-ip>` (see `Skills/tailscale-server-access/SKILL.md` for access + server context).

## What this skill covers

1. **Environment & secrets map** — `references/environment-map.md`:
   - Every verified env var **name** across all key containers (chat, ide, actions, analyticzs/PostHog, socialzs/Postiz, blastzs, n8n, crewai, Mission Control, Secret Access UI, Infisical, Activepieces, SSOReady, Probo, Nextcloud, MinIO) — grouped by app and by cross-cutting role (vault identity, Coolify control, DB layer, LLM layer, cloud/host, email/webhook, analytics, Genius platform, ops security).
   - Exact naming conventions and how variables are organized per container.
2. **Server context** — delegates to `Skills/tailscale-server-access/references/server-context.md` (containers, FQDNs, ports, services, cron, health playbook).

## Golden rules for secrets (non-negotiable)

1. **Never copy raw secret VALUES into any skill file, context doc, or chat log.** Reference variables by name; if a value must be shared, use a redaction (`sed 's/=.*/=<REDACTED>/'`) or a one-time share channel (email/SMS to Juelzs directly, or the Secret Access UI flow).
2. **Read env from a live container** instead of guessing:
   ```bash
   tailscale ssh root@<tailnet-ip> 'docker inspect <container> --format "{{range .Config.Env}}{{println .}}{{end}}"' \
     | sed 's/=.*/=<REDACTED>/'   # names (redact values) — or omit the sed if you need the value in-session and never echo it back
   ```
3. **Re-check before rotating/wiring anything**: confirm current usage of a variable with `docker inspect` before changing values in Coolify/Infisical — a token may be consumed by multiple containers (e.g. `ACTIONS_RAILWAY_TOKEN`, `GENIUS_DB`, `OPENAI_API_KEY` are cross-app).
4. **Keep the map fresh**: after env migrations, add a dated change-log line to `references/environment-map.md`. Never delete prior entries without noting why.
5. Container env changes require a redeploy/restart through Coolify (env files are baked at container create). Changing a `.env` file alone does NOT update a running container.

## Typical workflows

- **"Use the secrets accordingly"** → open `references/environment-map.md`, find the variable name(s) for the target app, pull current value from the live container (in-session only, never persisted), wire/compare/rotate, update the map change log if names/locations changed.
- **New service config** → locate the target app's env pattern in the map first; reuse existing variable names/roles instead of inventing new ones.
- **Diagnostics** → container-level env + logs (per access skill); cross-reference the same var names across consumers in the role table.
- **Audit** → sweep-all-names recipe in `references/environment-map.md`.
